## «Контроль новый» (parsec2)

Служба `ParsecIntegrationClient` начиная с 4.0.0 читает задания не из `CARDINDEV`,
а из собственной очереди `PARSEC_QUEUE`: триггеры бизнес-таблиц кладут туда событие,
служба меняет его статус и никогда не удаляет строку. `parsec2` показывает эту очередь.

Возможности страницы:

* сводка по статусам 0…6 с переходом в фильтр по клику;
* серверные фильтры: статус, операция, `SOURCE_TABLE`, поиск по ID/`ID_PEP`/`ID_CARD`/
  тексту ошибки/исполнителю/`DEDUP_KEY`, период по `CREATED_AT`, размер страницы;
* сортировка по колонкам (ID, статус, операция, попытки, создано, длительность);
* постраничный вывод (`select first … skip …`), страница подрезается, если фильтр её «сдвинул»;
* расшифровка: ФИО контакта по `ID_PEP`, название организации по `GUID` в `ID_CARD`;
* карточка события (`/parsec2/log/<id>`) — все поля строки и все попытки из `PARSEC_QUEUE_LOG`
  с раскрывающимся JSON `DETAILS`;
* действия (только POST, с подтверждением):
  * **Повторить** — статусы 3 и 4 → 0: `ATTEMPTS = 0`, `LEASE_UNTIL`, `STARTED_AT`,
    `FINISHED_AT`, `DURATION_MS`, `WORKER_ID`, `ERROR_*` очищаются, `NEXT_ATTEMPT = current_timestamp`;
  * **Отменить** — статусы 0 и 3 → 6: событие снимается с обработки.

`UPDATE` всегда выполняется с защитой `where id = N and status in (…)`, после чего строка
перечитывается: если служба успела изменить состояние, пользователь увидит сообщение,
а не «тихую» перезапись.

### Статусы

| Код | Значение | Кто ставит |
|---|---|---|
| 0 | новая | триггер/`PARSEC_ENQUEUE` |
| 1 | в работе | служба, `TryClaimQueueRow` |
| 2 | успешно | служба |
| 3 | ошибка, будет повтор | служба |
| 4 | ошибка, попытки исчерпаны (dead letter) | служба |
| 5 | пропущено (неизвестная операция, `SkipErrCode`) | служба |
| 6 | отменено (объект удалён/перепривязан) | триггеры |

### Особенности драйвера БД

База — Firebird/InterBase в WIN1251 через ODBC-драйвер `Gemini InterBase ODBC Driver`.
Две вещи, о которые легко споткнуться:

1. `PDO_ODBC` в этом проекте не умеет bind-параметры (Kohana использует `PDO::query()`,
   а не `prepare()`), поэтому значения подставляются в SQL как экранированные литералы —
   см. `Model_Parsec2::_esc()` (UTF-8 → CP1251 и удвоение кавычек).
2. Драйвер падает с `SQLFetchScroll` на timestamp-колонке с долями секунды
   (`LEASE_UNTIL` вида `2026-10-25 12:04:35.5081`). Поэтому все timestamp-поля
   выбираются как `cast(… as varchar(30))`, а `ORDER BY` идёт по исходным колонкам.

`PARSEC_QUEUE` описана в репозитории службы: `db/01_parsec_queue_ddl.sql`,
`db/02_parsec_enqueue.sql`, `db/03_parsec_queue_triggers.sql` и `db/README.md`.
